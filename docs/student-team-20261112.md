# 学生组队与老师名额刷新（2026-11-12）

## 使用流程

学生侧边栏新增“我的组队”，位于竞赛预览与报名管理之间。

1. 创建人填写队名、邀请学生；本人自动加入。已加入成员也可以继续邀请同学。邀请需要本人接受，支持拒绝、创建人撤销；创建人可移除成员，其他成员可退出。创建人退出使用解散操作，历史保留。
2. 待确认邀请处理完后，创建人从已加入成员中指定队长，包含创建人本人。被指定人需要单独接受或拒绝，其他学生不能代为确认。成员或邀请名单发生变化时恢复组队中，重新指定并确认队长。
3. 确认队长后显示“报名团队赛”。同队可报名多个团队赛，每次报名独立保存名单、姓名、专业及来源组队 ID；组队调整、退出或解散不修改已有报名。报名代表当前确认名单，成员在接受组队前可以看到此规则。
4. 报名窗口选择竞赛及指导老师，自动带入组队名单。成员已主动接受组队，无需重复接收报名邀请；导入确认来源记录到报名历史后正式提交，等待管理员审核。后端从队伍读取队名和名单，不信任请求中的成员及队名。
5. 指导老师选项显示当前剩余名额，满额不可选；展开选择时刷新，弹窗打开且页面可见期间每五秒刷新，可手动刷新并查看更新时间。提交前再次刷新，获取失败或已满额时拦截提交；后端在竞赛锁内再次校验。选择期间不预占名额，管理员审核时才最终占用。

个人赛保持原流程。历史报名的编辑、成员邀请及教师确认参赛后的名单锁定继续使用原规则。已有报名接口保持兼容；学生新建团队报名页面使用先组队流程。

组队业务通过站内通知进入对应队伍详情，进入时重新校验角色及队伍参与权限。所有成员状态变更、队长确认、消息和操作历史在同一事务保存。

## 接口

新增十个方法与路径组合，均限学生；列表、详情与操作进一步检查本人关系：

| 方法 | 路径 | 功能 |
| --- | --- | --- |
| GET | `/api/team/mine` | 本人创建或加入的队伍 |
| GET | `/api/team/invitations` | 本人待处理组队邀请 |
| GET | `/api/team/{id}` | 队伍成员、状态与操作历史 |
| POST | `/api/team` | 创建队伍及邀请 |
| POST | `/api/team/{id}/invitations` | 已加入成员邀请其他学生 |
| PUT | `/api/team/{id}/response` | 被邀请人接受或拒绝 |
| PUT | `/api/team/{id}/captain` | 创建人指定候选队长 |
| PUT | `/api/team/{id}/captain/response` | 被指定人确认或拒绝队长 |
| DELETE | `/api/team/{id}/members/{userId}` | 移除、退出或撤销邀请，保留历史 |
| DELETE | `/api/team/{id}` | 逻辑解散队伍，保留历史 |

复用 `POST /api/registration`，新增可选 `sourceTeamId`：有值时必须是已确认的本人队长，服务端从该队读取名单，重新校验时间、赛制、学生状态、专业、跨专业规则、人数、重复参赛和教师资格及剩余名额。无值的原请求保持兼容。既有获奖与指导统计仍按报名名单计算，不因可复用组队重复计数。

## 数据迁移

在 05 迁移完成后执行 `sql/migrations/20261112_06_student_team.sql`。增加 `student_team`、`student_team_member`，以及报名的 `source_team_id`。旧报名来源留空，原成员、指导、获奖、邀请与历史数据不变。无须把旧报名伪造为可复用组队；旧团队可继续按原报名规则管理。

本地 `competition` 已备份、恢复验证、演练并完成迁移。原有 19 张表全部旧字段和行数摘要比对一致；迁移后为 21 张表、225 个字段，核对 40 个索引和 12 个实体，无缺失或映射错误。迁移结果和备份位置记录在忽略的 `output/student-team-migration-result.json`，备份位于 `output/backups/`。

其他环境部署需先停止后端写入，完成备份和迁移，再发布前后端。脚本只执行一次，不自动重复执行；本轮没有修改其他服务器。
